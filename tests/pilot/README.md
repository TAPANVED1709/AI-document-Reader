# Phase 14 synthetic persisted-pipeline pilot

Fixtures and truth are authored by `generate.py`, which imports no application parser or normalizer. The catalog's printed ranges are invented engineering inputs. All 31 PDFs (446 rows) are synthetic and contain no patient identifiers. User-described simple glucose, multipage biochemistry and multisection layouts were used; no real source PDF was available or ingested.

From repository root:

```powershell
python -m pip install -r apps/ai-service/requirements.txt -r tests/pilot/requirements.txt
python tests/pilot/generate.py
python -m pytest -q tests/pilot/test_compare.py
python tests/pilot/run_pipeline.py --label before
# Only after recording demonstrated defects and applying minimal fixes:
python tests/pilot/run_pipeline.py --label after
python tests/pilot/compare.py tests/pilot/runs/after
```

The catalog/layout is repeatable, but PDF document IDs can change regenerated bytes. Do not regenerate a frozen dataset during comparison; use the committed PDFs. `manifest.json` verifies both PDF and truth hashes, including bytes/newlines. Run directories must be new; existing machine evidence is never overwritten by the pipeline runner. Standalone comparison can regenerate derived metrics from the preserved machine snapshots.

Requires local Docker with SQL Server, API and AI images; loopback port 18080 must be free. A unique Compose project and temporary strong credentials isolate each run. The runner seeds synthetic role/organization/grant data only in its own disposable database; ingestion, queue, worker, OCR and persistence use production endpoints. No production rate limits or security checks are disabled. Only the isolated project's containers are stopped. Its volumes are retained for forensic inspection and should be removed by their owner after the agreed retention period; credentials are not written to artifacts.

Images are generated at 200 DPI for ordinary scans and 135 DPI with mild blur/contrast reduction for degraded scans. Tesseract renders at the application's 300 DPI. Faded decimal ink and printed I/l substitutions retain the clean authored truth, making damage measurable rather than changing truth to OCR output. An ideal reviewer must examine these sources; no algorithm can recover information entirely erased from an arbitrary source.

`compare.py` checks all explicit fields, including nulls. ASP.NET omits null properties: omission and null both mean absence, but neither matches an expected non-null field. Numeric fields use exact Decimal equality. Only whitespace, Unicode dash typography, and spacing around range separators/operators are normalized (for example `4.0-11.0` equals `4.0 - 11.0`; `40-11.0` does not). Raw values are retained in comparison exports. Qualitative strings remain exact and case-sensitive. Missing rows count as failures in applicable accuracy denominators. False positives and missed rows are separately enumerated. One-to-one matching uses names/page/method/source position and never values, units or ranges. Matching fuzzy names is an evaluation heuristic; every mapped row is exported for human inspection. Association accuracy requires the name, value, unit, reference, page, section and method bundle to be correct. Wrong-association counts separately include identity/page/section/method mismatches and detectable value swaps; they do not prove a causal OCR mechanism.

Review metrics treat content errors or ground-truth ambiguity as positives. Correct rows reviewed unnecessarily are false positives. Missed rows count as false negatives, not unsafe accepted results because no result exists. Extra auto-accepted predictions count as unsafe association errors. A row is safely routed only if both `reviewRequired=true` and `reviewState=REVIEW_REQUIRED`. Human-corrected output is never used for grading.

Format groups overlap (e.g. a scanned multi-page report), so their counts should not be summed. Panel assignment follows authored expected rows; unmatched predictions use Other, explicitly avoiding an invented panel. Group percentages with no denominator are null. Technical verdict FAIL covers unsafe errors, missed/extra rows, wrong associations or wrong document classification; REVIEW includes safe errors, ambiguities and unnecessary reviews; PASS requires complete extraction with no review remaining.
